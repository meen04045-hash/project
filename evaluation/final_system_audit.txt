1. EXECUTIVE SUMMARY
--------------------
The active Flask application has three routes: GET /, POST /callback, and POST /send. The normal LINE text-message path uses all six ML tasks, applies explicit/model-based safety logic, writes chat_logs, and sends a LINE reply. The LIFF result path verifies a LINE ID token, saves results under the verified sub, and then pushes a LINE message. Existing score, identity, callback-signature, sensitive-console-log, and LIFF-init protections remain present.

Priority totals: MUST FIX BEFORE FINAL SUBMISSION = 3; SHOULD FIX IF TIME = 9; ACCEPTABLE AS LIMITATION = 3. These are audit findings, not patches. The main proven concerns are (1) client-controlled assessment reports are accepted as authoritative results, (2) substring safety matching can misread a negated phrase, and (3) missing/corrupt model artifacts trigger training and artifact writes during Flask import. Deployment readiness remains unverified: the Render service is reported Suspended/on an older commit, and real LINE/Firestore configuration was not tested.

Flow A — ordinary LINE text event:

5) app.py:610-629 writes chat_logs with user_id, raw text, and full prediction; write errors are logged by exception class and processing continues.
6) app.py:636-638 writes emotion/problem to in-memory user_state. app.py:664-765 then evaluates hard-coded safety phrases, risk label/confidence, and crisis intent/confidence. app.py:785-867 composes a normal response only if safety did not trigger.

Documentation correction: chat_logs is written BEFORE the safety decision and LINE reply, not after. The two exact command branches bypass inference/logging. A saved log does not prove a reply was delivered.

Flow B — LIFF assessment/result:
1) app.py:357-360 index() serves templates/index.html. templates/index.html:857-878 runs liff.init with the hard-coded LIFF ID; login is requested if needed, and an init failure shows view-liff-error with reload retry (lines 533-541).

3) templates/index.html:1126-1190 sendToBot() disables the send button, obtains liff.getIDToken(), checks finalReport, then POSTs score to same-origin /send with Authorization: Bearer token. No client userId is sent by the active template.

5) app.py:409-419 calls save_result(); app.py:75-79 sets results/{verified_sub} with result text. If save fails, push is skipped and JSON saved=false/pushed=false is returned.
6) app.py:421-435 calls push_message(); 200 means saved=true/pushed=true, 502 means saved=true/pushed=false. The frontend parses JSON even for non-2xx, disables retry in its current page when saved=true, and re-enables it when save is unconfirmed/failed.
Documentation correction: Firestore save precedes push. A 502 with saved=true is partial success, not a failed save; push timeout may leave actual delivery unknown.

7. STATE / IDEMPOTENCY / DUPLICATION
------------------------------------
- /send: the disabled button prevents two rapid clicks in the same loaded page. A refresh/new tab/network retry can submit again. results/{sub}.set overwrites one document but repeats the write and may send another LINE push. After a push timeout, 502 saved=true/pushed=false cannot establish whether LINE delivered; the frontend blocks retry only until the page is reloaded. No backend request key or idempotency check exists (S-02).
- /callback: the code does not inspect webhookEventId or maintain a processed-event store. A redelivered LINE message can run inference again, add another chat_logs document, and call reply_message again (S-03). Any LINE reply-token handling outcome on replay requires real-service evidence.
- user_state: an ever-growing process-local dictionary is created even for command messages. The stored fields are never read. Gunicorn workers would each have separate dictionaries; restart clears them. Since no current read uses this state, no current cross-worker functional failure is proven, but memory growth is real (S-01).
- Firestore documents are shared/persistent across workers; the dictionary is not. There is no persistent server-side conversation state in the current app.

10. MUST FIX BEFORE FINAL SUBMISSION — 3 FINDINGS
-------------------------------------------------
M-01 | severity HIGH | Assessment result integrity
Evidence: templates/index.html:1151-1159 submits a client-composed score string; app.py:370-377 only checks type/nonblank and app.py:409-429 stores/pushes it as an assessment result. Any authenticated client can modify the string before submission, including scores not produced by 2Q/9Q/8Q. There is also no length/shape bound.
Affected: /send, Firestore results, LINE push, interpretation of saved assessments.
Minimal recommended action: define a trusted server-side assessment contract (e.g. submit answers and verify/recompute the report) and a size bound before representing stored text as a validated assessment. If the project intentionally accepts self-reported text, label it explicitly as unverified instead of claiming computed integrity.
Risk of changing now: HIGH; it changes the frontend/backend contract and needs tests across all assessment branches. No scoring logic was changed here.

M-02 | severity HIGH | Safety phrase negation false positive
Evidence: app.py:694-723 uses substring matching; an ordinary negated phrase such as "ไม่อยากตาย" contains the configured substring "อยากตาย". explicit_safety then forces the crisis response at app.py:758-781 regardless of model output.
Affected: LINE message safety decision and user-facing reply.
Minimal recommended action: add regression cases for negated/contextual phrases and narrowly adjust the explicit matching rule with safety-domain review.
Risk of changing now: HIGH; a broad exception may create false negatives for genuine danger. Do not alter the rule without safety review and tests.

M-03 | severity HIGH | Implicit model retraining during server import
Evidence: app.py:14 imports predict_all; ai_model.py:254-260 calls get_model() six times at import. ai_model.py:184-199 trains, writes evaluation files, and joblib.dump()s model/vectorizer files when a pair is missing or loading raises an exception. This can silently replace frozen production artifacts or fail startup on a read-only/limited filesystem.
Affected: startup, model integrity, deployment reproducibility, evaluation artifacts.
Minimal recommended action: make serving fail explicitly on missing/incompatible artifacts and keep training only in an explicit offline command; validate all 12 artifacts against the actual target runtime before deployment.
Risk of changing now: MEDIUM; a bad artifact would stop startup instead of self-recovering, which is the safer behavior for a frozen model but requires deployment checks. No training was run here.
