1. AUTOMATED / MOCK TESTS RUN
-----------------------------
A. LINE webhook — PASS (local SDK dispatch + Flask mock)
- Missing X-Line-Signature -> HTTP 400.
- Invalid signature -> HTTP 400.
- Four valid signed text events dispatched to handle_message, with four mocked LINE replies and four mocked chat_logs writes.
- An unsupported-for-this-handler LINE follow event returned HTTP 200 without a server crash or unintended reply.
- Normal response and three safety paths were exercised: explicit phrase, high-confidence model risk, and high-confidence crisis intent.
- Real linebot WebhookHandler was used for signature/dispatch; LINE reply and Firestore were mocked. The SDK emitted a deprecation warning for linebot.v2-style WebhookHandler; no migration was made.

B. ML inference — PASS (actual serialized artifacts, local only)
- Loaded all six existing model/vectorizer pairs directly from models/ without importing ai_model.py startup code. This avoided its train-and-save fallback.
- Called the current clean_text, tokenize, predict_with_confidence, and predict_all functions in memory with seven temporary smoke inputs: normal, depression, stress, risk_passive, risk_suicidal_ideation, risk_suicide_plan, and risk_immediate_danger.
- Every input returned all six task labels and six confidence values; no inference exception. Labels were valid model classes and confidence values were in [0, 1].
- SHA-256 values of all 12 production model artifacts matched before and after loading/inference. No train_model, fit, or joblib.dump call was made.
- One temporary input intended to probe passive wording was predicted as risk_suicidal_ideation. This is a smoke-test observation only, not an accuracy estimate or a finding that any dataset label is wrong.
- An initial test-harness assertion expected support_need_conf rather than the code's support_conf; the harness was corrected and rerun. This was not an application failure. No source file changed.

C. /send — PASS (Flask test client with mocked LINE verify, Firestore and push)
- Invalid JSON -> 400, saved=false, pushed=false.
- Missing score, null, empty, whitespace-only, number, boolean, list, object -> 400 JSON; zero verify/save/push calls.
- Missing/malformed Authorization (four cases) -> 401; no verify/save/push.
- Invalid LINE ID token mock -> 401; verify timeout mock -> 503; no save/push.
- Valid mocked LINE verification -> backend used verified sub for Firestore document and LINE push, ignoring forged user_id and userId fields supplied by client.
- Firestore save + LINE push success -> 200, saved=true, pushed=true.
- Firestore save failure -> 500, saved=false, pushed=false; push was not called.
- Save success + LINE push failure -> 502, saved=true, pushed=false.
- Save success + push timeout -> 502, saved=true, pushed=false; actual delivery remains ambiguous.
- Captured error logs did not contain the sentinel assessment text, token, or verified user ID.

D. Identity — PASS (local code and mock)
- LIFF uses getIDToken() and sends Authorization: Bearer <token>.
- Backend sends id_token and LINE_LOGIN_CHANNEL_ID as client_id to POST https://api.line.me/oauth2/v2.1/verify and uses the verified response sub as user_id.
- The client request body contains score only in the tested frontend path; a forged client user ID was ignored in the backend mock.
- Current app/frontend diagnostic logs did not expose the tested token, Authorization value, or raw user text.
- Real LINE Login channel configuration, ID-token validity, and live verify service were not tested.

E. LIFF frontend — PASS (Node runtime with mock DOM, LIFF and fetch)
- JavaScript parsed; successful LIFF init and login scheduled the welcome view.
- Failed LIFF init showed the error view without scheduling welcome; retry markup reloads the page.
- One mocked assessment path progressed 2Q -> 9Q -> 8Q -> result and produced a nonempty finalReport. This is path verification, not a scoring audit.
- sendToBot called getIDToken(), sent a Bearer token and score-only JSON body to /send.
- Two immediate send clicks produced one fetch; success left the send button disabled.
- A saved=false response and a network failure re-enabled the button for retry.
- A 502 saved=true/pushed=false response kept the button disabled and notified the user that the result was saved but LINE delivery failed.
- Sensitive text placed in mocked LIFF/fetch exception messages was not printed by frontend logs.

4. NON-BLOCKING RISKS / OBSERVATIONS
------------------------------------
- Current LINE SDK WebhookHandler emits a deprecation warning; migration was outside this test-only scope.
- Actual Flow 1 stores chat_logs before safety selection and LINE reply; a later reply failure can leave a saved log with no reply. The listed schematic order should not be mistaken for the code's execution order.
- Duplicate webhook delivery and repeated /send after refresh are not protected by backend deduplication/idempotency. The send button prevents immediate double clicks in one page instance only.
- A push timeout after a successful save returns saved=true/pushed=false even when the delivery outcome may be unknown.
- score/finalReport content remains client-authoritative after identity verification.
- verify endpoint error mapping and user_state cleanup remain outside this round.
- ai_model.py get_model can train, evaluate, and write artifacts if a model/vectorizer file is absent or load fails. All 12 current artifacts existed and loaded for this test; full startup fallback was deliberately not invoked.
No item above was changed in this round.
