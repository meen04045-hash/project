SERVER-AUTHORITATIVE ASSESSMENT RESULT FIX — 2026-09-30
======================================================

Scope: MUST FIX #3 only. The frozen 2Q/9Q/8Q values, transitions,
thresholds, and report wording were copied from templates/index.html;
their correctness was not reinterpreted or clinically audited.

1. OLD TRUST BOUNDARY
---------------------
LIFF calculated the assessment and sent {"score": finalReport}. /send
checked only that score was a nonblank string. A valid LINE ID token
established user identity via verified sub, but did not establish that
the client-generated score/report matched answers. The submitted string
was saved as results/<verified sub>.result and used in LINE push.

2. NEW REQUEST SCHEMA
---------------------
sendToBot() now posts this JSON shape to same-origin /send:
  {"answers_2q": [two 0/1 integers],
   "answers_9q": [nine 0..3 integers] or [],
   "answers_8q": [eight 0/1 integers] or []}
The Authorization: Bearer <LIFF ID token> header is unchanged. An empty
9Q or 8Q array is sent only for a questionnaire not reached in the final
assessment path. No score, finalReport, risk level, or user_id is sent.
The browser still calculates finalReport for its existing result screen;
that value is no longer authoritative for persistence or LINE push.

3. BACKEND VALIDATION
---------------------
app.py:validate_assessment_answers() requires a JSON object with exactly
the three fields above. It checks list type, exact length, Python int
type (so booleans are rejected), and allowed value ranges. It does not
coerce strings/floats or accept null, missing keys, extra keys, negative
values, or out-of-range values. Invalid payloads return JSON
{saved:false,pushed:false} with HTTP 400 before LINE verification,
Firestore save, or LINE push. Old score-only requests and client-supplied
result/user_id fields are rejected.

4. SERVER-SIDE SCORING AND FLOW CONSISTENCY
-------------------------------------------
app.py:build_assessment_result() generates the exact report string from
validated answers. The copied rules are:
- 2Q sum 0: finish with the existing 2Q normal report; 9Q/8Q must be [].
- 2Q sum above 0: require nine 9Q answers. The existing 9Q total and item
  9 test (total >= 7 OR item 9 >= 1) determine whether 8Q is required.
- If 8Q is not reached, it must be []; if reached, exactly eight answers
  are required. The existing Q8 weights (1,2,6,8,9,4,10,4), 9Q text
  thresholds, and 8Q text thresholds are preserved.
- A payload that skips a required questionnaire or includes one outside
  its branch is rejected with HTTP 400.

The frontend records the step of the report most recently generated.
This is used only to omit arrays from branches not reached, including
answers left in browser state after navigating back. The server does not
receive or trust that step; it derives the valid branch from answers.
No scoring rule or visible result screen was changed.

5. IDENTITY, FIRESTORE, LINE PUSH, AND RESPONSE CONTRACT
--------------------------------------------------------
After validation, /send retains its LINE POST /oauth2/v2.1/verify call
and uses the returned sub as user_id. No client user_id is accepted.
save_result() still writes results/<verified sub> with the existing
{"result": text} field, but text is now generated by the backend.
The LINE push still targets verified sub and uses the same backend text.
No answers were added to Firestore; no schema migration was made.
Response contract remains: 200 saved=true/pushed=true; 502 saved=true/
pushed=false; 500 saved=false/pushed=false for save failure; 400 both
false for invalid payload; existing 401/503 authentication and LINE
verification error mapping is unchanged. Save failure still prevents push.

7. REMAINING LIMITATIONS / MIGRATION
------------------------------------
- The backend can verify deterministic score/report consistency with
  submitted answers, but cannot prove that a person answered truthfully
  or that the questionnaire was completed through the UI.
- Frontend and backend must be deployed together. A stale cached LIFF page
  sending the former score-only schema will receive HTTP 400 until reload;
  the old insecure schema is intentionally not accepted.
- Scoring/report logic now exists in both JavaScript (preview) and Python
  (authoritative result); future rule changes require parity tests.
- Duplicate /send requests and ambiguous LINE push timeouts remain separate
  known risks. This change does not add backend idempotency.
- Live LINE/LIFF/Firestore behavior was not tested here; all tests used
  local mocks. No clinical validation is implied.
